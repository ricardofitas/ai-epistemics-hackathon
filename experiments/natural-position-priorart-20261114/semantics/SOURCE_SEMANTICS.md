## Finding

The separate correct-answer and distractor fields are legitimate source storage. A fixed candidate-array index is also legitimate for a likelihood evaluator that independently scores each answer continuation. The One-Eval generation path turns the semantic gold field into displayed option A, without a permutation and corresponding label remap. This exposes a deterministic answer-position rule. It is stronger than a model's ordinary sensitivity to candidate order. It does not establish that the benchmark authors' own results were affected.

## Exact One-Eval causal path

Revision: `OpenDCAI/One-Eval@8aba20ad17ee2c7d2391162ac03ffaebcbb17506`.

1. **Gallery order.** Each of CUPCase, SciQ, and GPQA declares `key3_q_choices_a`. Its `meta.key_mapping.input_choices_key` and parser `choice_text_fields` put the semantic correct field first, followed by the three distractors. `meta.evaluation.prediction_mode` is `generation`; the gallery prompts request `<answer>CHOICE</answer>`. The gallery contains no option permutation/remap for these entries.
2. **Native merge and labeling.** `DataFlowEvalTool._preprocess_dataframe:283-332` builds `merged_choices` by iterating the configured field list in its existing order. `_choices_text:401-403` and the generator's `_format_choices_text:96-102` enumerate that order as A, B, C, D. No shuffle intervenes. Thus the source gold text occupies displayed A in all 5,010 audited source rows.
3. **Generation branch.** `DataFlowEvalTool.run_eval:1102-1138` sets `force_generate` for API single-choice evaluation (or enabled judge). At `1184-1191` API serving selects `parse_choice_acc` because it lacks likelihood hooks. This matters: `BenchAnswerGenerator._need_generation:188-197` normally skips single-choice generation when force is absent. The existing source-loaded audit explicitly forces generation; it is not evidence about an unforced local likelihood run or a complete CLI run.
4. **Actual prompt construction.** `_resolve_prompt_template:411-427` selects the gallery template and normalizes brace syntax. Wheel `BenchAnswerGenerator._build_prompt:129-172` supplies only generic `question`, `context`, `choices`, `choices_text`, and `eval_type`, not all original source-column names. Wheel `FormatStrPrompt.build_prompt:18-31` performs string replacement rather than Jinja evaluation. Consequently source-named CUPCase `clean_case_presentation` and GPQA `Question` remain unresolved; lowercase SciQ `question` is supplied. SciQ `support` remains unresolved because the generic key is `context`. Converting placeholders to double braces also leaves an outer brace pair around substituted values. Existing prompt-presence receipts show own-question presence 0/3,562 CUPCase, 1,000/1,000 SciQ, 0/448 GPQA. Choices remain present and correctly ordered. These prompt defects are distinct from the answer-position rule.
5. **Diagnostic rescore.** On the API parse branch `run_eval:1269-1283` calls `_rescore_choice_single` on `generated_ans`, then marks stats diagnostic. That function parses generated text and source-answer text using the same choice parser, computes diagnostic accuracy, and writes `eval_pred = float(labels.index(predicted_letter))` (`850-971`). The parser checks numeric indices and explicit answer patterns before matching option text (`choice.py:98-161`), so a source correct text is not guaranteed to normalize to A despite occupying candidate A. This explains why positional coverage and measured diagnostic accuracy must be reported separately.
6. **Metric-stage mismatch.** `DataFlowEvalNode:197-201` chooses `pred_key='eval_pred'` for single-choice tasks. `MetricRunner:274-290,404-406` honors this field. The audit records contain floating values such as `0.0`, not the tagged generation or integer index. The choice parser recognizes integers or integer-shaped strings, but not float-shaped strings such as `0.0`; the ordinary metric also fails to extract a choice letter. Both metric variants in the existing audit therefore return zero. Substituting `generated_ans` would test another boundary, not the unchanged primary path.
7. **Report selection.** Despite `_mark_stats_diagnostic` setting `role='diagnostic'` and `display_as_primary=False`, `ReportGenAgent._resolve_report_score:254-260` returns `bench.meta['eval_result']['accuracy']`, then `score`, and otherwise zero. It does not inspect the diagnostic flags, gallery `score_source`, or the passed metric-stage score. `_build_bench_summaries:198-249` calls that function and labels its output `primary_score`. The existing audit executed this exact selection function; it did not generate a full final report or run the full CLI.
